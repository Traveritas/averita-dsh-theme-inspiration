# dsh-theme-averita 性能检查报告

> 2026-11-07，通过 CDP（9222）连上正在运行的 DSH Desktop 实测。
> 环境：AMD Radeon 610M（ANGLE / D3D11，集显）、DPR 1.25、视口 1282×822、
> 页面 186 张样式表 / 4700+ 节点。测量时本会话正在流式输出，噪声已用交替 A/B 与中位数压掉。

## 结论

**主线程空闲时主题几乎不花钱，但有两个真实的性能问题：**

| # | 问题 | 严重度 | 现状数据 |
|---|---|---|---|
| 1 | 滑杆拖动（缩放 / 浓淡 / 呼吸）会掉到 ~15fps | **高** | 帧间隔 p50 = 66.8ms（应为 16.7ms） |
| 2 | 切主题一次卡 ~36ms（四套轮换可见顿感） | 中 | 单次 36.4ms，p95 50.8ms |
| 3 | 主题样式表让样式重算慢 ~3 倍 | 中 | 4 秒内 547ms vs 183ms |
| 4 | `:has(~)` 那条最后回复动画在 240+ turn 时劣化 | 低 | 暂未稳定复现，留观察 |

流光的 WebGL 本身**没问题**：稳定 26fps 绘制（锁 30fps）、80 次/秒 `drawArrays` 只占脚本时间 52ms/5s，
主线程不参与着色。点阵的 CSS 动画也不贵（`over20` 帧数与背景关闭时持平）。

---

## 问题 1（高）：滑杆拖动掉到 15fps

### 现象

`--av-scale` / `--av-depth` / `--av-breathe-min` 写在 `html` 行内样式上。
拖动时每次 `onChange` 都会改 `html` 的 `style` 属性，**整棵文档树的继承样式全部失效**。

同一操作、不同写法，交替 3 轮测得的帧间隔：

| 每帧写什么 | p50 | p95 | 1.5 秒内帧数 |
|---|---|---|---|
| `html` 行内 `--av-scale`（**现状**） | **66.7ms** | 83.5ms | 23 |
| `html` 改一个无人消费的 data 属性 | 16.7ms | 16.8ms | 85 |
| 什么都不写 | 16.7ms | 33.4ms | 70 |

时间去向（1.5 秒、19 帧的区间内）：

| 阶段 | 耗时 |
|---|---|
| 样式重算（RecalcStyle） | **1383ms** ← 就是它 |
| 布局（Layout） | 53ms |
| 脚本 | 19ms |

即：几乎全部时间花在样式重算上，与 JS 无关。

### 根因

`--av-*` 是**未注册的自定义属性**，按规范它们是可继承属性。改 `html` 上的值 =
整棵树所有节点的 `var()` 引用都可能变化，Blink 只能全部重算。

### 验证过的修复方向

| 写法 | 值能传到 `body::before` | 帧率 |
|---|---|---|
| A `html` 写 `--av-scale`（现状，未注册） | ✅ | 66.7ms ❌ |
| B `body` 写 `--av-scale`（未注册） | ✅ | 66.7ms ❌ |
| C `body` 写 + `@property { inherits: false }` | ❌ | **16.7ms** ✅ |
| D `body` 写 + `@property { inherits: true }` | ✅ | 66.7ms ❌ |

只用 `inherits: false` 能达到 60fps，但值传不到 `body::before`（伪元素不继承宿主元素的自定义属性）——
**所以不能只加一行 `@property` 了事**，那会静默破坏背景。

另测：把点阵层从 `body::before` 换成真实 `<div>`，配 `@property inherits:false`，
既 **16.7ms / 79 帧**，`mask-size` 也确实跟着变成 `40px auto`（值生效）。

### 建议（需要你拍板）

**方案甲 —— 点阵层从伪元素搬到真实 div（推荐）**
- 点阵层改成 `body > .av-dots`，`@property` 注册三个变量为 `inherits: false`，写在 `html` 上。
- 收益：拖滑杆从 15fps → 60fps，且样式重算不再扫全树（问题 3 一并改善）。
- 代价：插入一个 DOM 节点（现在插件号称"不插 DOM"），`html[data-av-bg="flow"] body::before { content: none }`
  这类写法要跟着改；组件单独复用时需要多带一段结构说明。

**方案乙 —— 只降增量写入频率**
- 拖动时用 `requestAnimationFrame` 合并，或 `input` 事件节流到 ~30Hz。
- 收益：改动极小，掉帧数减半。
- 代价：治标不治本，仍会掉到 30fps 档；而且松手后才真正生效的手感会变"沉稳"。

**方案丙 —— 保持现状，只文档说明**
- 什么都不改，在 README 里注明"拖动缩放 / 浓淡滑杆时会掉帧"。
- 代价：这是用户最容易感知的卡顿点。

## 问题 2（中）：切主题一次 36ms

四套主题轮换 8 轮、每轮强制读写一次布局，单次中位数 **36.4ms**，p95 50.8ms。
一帧 16.7ms 的预算下这是一次明显掉帧，且设置面板里连点四张卡片会连掉四帧。

原因同上：`selectTheme` 同时改 `html` 的 `data-av-theme` 属性 + 通过 `ctx.theme.overrideTokens`
往 `body` 行内写 **196 条** `--dsw-*` 令牌（`body` 行内样式共 9350 字节）。
这两处都是全树失效源。

这条属于"切主题本来就重，但可以更轻"：
- 令牌 196 条必须写（宿主契约），但可以只写一套、让深色靠 `:has()` 切——现在已经是这个思路；
- 真正能减的是**不要同时改 `html` 属性**，或者把主题色也走 `@property` 注册。

收益预期有限（一次 36ms 不会消失，可能降到 20-25ms）。**这条我倾向于不改**，除非你觉得切主题的顿感确实碍事。

## 问题 3（中）：主题样式表让样式重算慢约 3 倍

交替 A/B（每档 4 秒 × 3 轮，中位数）：

| 条件 | RecalcStyle 次数 | 重算耗时 | 任务总时 |
|---|---|---|---|
| 主题开 | 262 | **547ms** | 1397ms |
| 主题关 | 250 | **183ms** | 1040ms |

重算次数几乎一样（262 vs 250），耗时却是 3 倍 —— 说明**单次重算变贵了**，不是触发变多。

静态统计：45275 字节 CSS、154 条规则、24 条含 `:has()`、46 处 `color-mix()`、
14 处 `mask-*`、8 处 `!important`。

分规则组 A/B（每档 3 秒 × 2 轮）：

| 变体 | RecalcStyle ms |
|---|---|
| 完整表 | 606 |
| 删掉最后回复动画那条 | 472 |
| 再删掉全部 `:has()` 规则 | 302 |
| 再删掉 paper / star 装饰 | 252 |

`:has()` 规则约占一半（606 → 302）。它们是深色适配（`html:has(body[data-ds-dark-theme])`）和首屏定位。

**这里有个便宜的改法**：`html:has(body[data-ds-dark-theme])` 完全可以改成
`body[data-ds-dark-theme]` 后代选择器（或直接挂在 `html[data-theme-mode="dark"]` 上），
一类 `:has()` 就没了。26 处里约 18 处是这种"用 `:has` 看 body 上有没有某个属性"的模式。

## 问题 4（低）：`:has(~)` 那条动画在长会话里劣化

`[data-chat-turn]:not(:has(~ [data-chat-turn]))` 让每个 turn 都去数"后面还有没有兄弟"，
是 O(n²) 形状。240 个 turn 时第一次测得 13.7ms → 53.9ms（+40ms），但后续 4 轮交替**没能复现**
（16.4 vs 16.9ms），怀疑首次命中与布局缓存有关。

**不建议现在动**（这是"只给最后一条回复挂进入动画"的唯一纯 CSS 写法），
但如果你有超长会话，值得回头再量一次。

## 流光的实测数据（结论：健康）

| 项目 | 数据 |
|---|---|
| 绘制 | 26fps（锁 30fps 目标，因 60Hz 下是每 2 帧一次，实际 25-27） |
| 每帧 `drawArrays` | 1 次，5 秒 131 次 |
| 脚本时间 | 52ms / 5s（含宿主全部脚本），主题自身 profile 里 `frame` 只占 1.2ms / 6.3s |
| 显存 / 分辨率 | 257×165（视口 1/5，符合设计） |
| 上下文丢失 → 恢复 | ✅ 正常：lost=false 后 `drawArrays` 恢复 27 次/秒 |
| 主线程 CPU profile | `(idle)` 70%、`(program)` 28.6%，热点里跟主题有关的只有 `uniform1f` / `drawArrays` 各 2.4ms / 1.8ms |

点阵 / 流光 / 背景关闭三种形态的帧节奏基本一致（p50 均 16.7ms），
说明**背景不是掉帧源**。唯一例外是 4× 缩放时 `over20` 从 4 涨到 9，符合 README 里
「极端缩放会放大合成面积」的说明。

## 代码层面看到的其他点（不影响当前性能，但值得知道）

1. **`BrandMark` 每帧重建 SVG 的路径还在**，只是被 `STAR_MOTION = false` 关掉。
   注释里写得很清楚（每 33ms 重写 `innerHTML` 会让宿主 `:has()` 整片失效），
   这个开关一旦打开就是灾难级开销。建议要么删掉这条死路径，要么加显式护栏。
2. **`HeroMark` 的 `spin` 每次 hover 都重画整颗星**（520ms / 每帧 1 次 `innerHTML`），
   只影响首屏、且是交互触发，可以接受。
3. **`flow.js` 的 `draw()` 每帧 `new Float32Array(palette.flat())`** —— 每秒 30 次小对象分配，
   换成复用数组能省一点 GC（profile 里 GC 只占 0.4%，所以优先级低）。
4. **`resolveFlowColor` 每次换色都建一个隐藏 `<span>` 挂到 body 再读计算值**，
   只在切主题 / 色板时触发，可接受。
5. **`html:not([data-av-theme])` 兜底值在 dots 和 theme.css 里各写了一份**（`--av-space` / `--av-dot`），
   改色时容易漏改一处。

## 建议的优先级

1. **先修滑杆掉帧**（问题 1）—— 这是唯一用户每次调外观都会撞上的卡顿。
2. 顺手把 `html:has(body[data-ds-dark-theme])` 改成 `body[data-ds-dark-theme]` 后代写法（问题 3），改动小、风险低。
3. 切主题的 36ms 和长会话的 `:has(~)` 先记着，不改。
4. 删掉或加护栏住 `BrandMark` 的死帧循环。
